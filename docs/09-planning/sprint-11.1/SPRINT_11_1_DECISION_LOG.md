# Architecture decisions

## ADR 11.1-17 — Four bounded batches and independent cloud acceptance

The user's fix request authorizes the explicit all-specialists goal. Four calls
cover nine roles with compact, separately validated outputs: Gemini financial/
schedule/resource; native Puter risk/governance/agile; Groq team/PMO then executive.
This supersedes ADR 16's initial allocation after measured Groq three-domain
schema/truncation failures. Smaller Groq synthesis batches passed. Assignment remains
operational/provisional; no accuracy ranking, qualification or activation follows.

Keep 512/4/2/90 limits, whole source excerpts, immutable per-case/account history,
same-run quota waiting and live authority. A repair may leave a later batch partial.
Reject private assessment answers in multi-role batches. Require primary-scope
financial/resource citations and qualitative model prose; Python owns numbers.
Freeze independent labels before fresh held-out acceptance. Cloud measurements bind
service identity and hashes, without fake local hardware fields or weight training.
The user will nominate the reviewer. [Current evidence and remaining gates](../../verification/sprint11_1/CLOUD_BATCH_REPAIR.md).

## ADR 11.1-16 — Three cloud candidates with measured, unqualified role assignment

User requested Ollama shutdown, Gemini/Groq/Puter across nine roles, and tuning when
feasible. Stop local processes while preserving weights/startup. The provisional
three-roles/provider policy restricts assignment independently of qualification;
unqualified profiles cannot gain tenant scope or execute through production admission.
Native Puter uses the account Free allowance, fixed service/model alias binding and
actual finish/usage metadata, never its paid compatible gateway. Gemini all-required
schemas and versioned positive/missing examples address observed protocol omissions;
numeric/evidence/privacy validators and 512/4/2/90 limits are unchanged. Pending tasks
cannot silently adopt a changed prompt hash. Fine-tuning is unavailable on these
current free paths; original reference-informed synthetic examples support prompting
and future lawful exports, not invented weight training or independent labels.

26 calibration calls show initial supported hard-valid output for every role, with
two Groq negative cases rejected. Retain every failure/root/account counter and
do not promote from this sample. Independent per-class/held-out cloud acceptance
and scoped rollout remain required. See [implementation guide](../../03-sprints/active/sprint-11.1/CLOUD_SPECIALISTS.md)
and [review packet](../../verification/sprint11_1/CLOUD_CALIBRATION_RESULTS.md).

Status: selected design decisions; implementation checkpoint is linked from the package index. No normal deployment or real-model qualification is claimed. Each ID maps to requirements in [traceability](SPRINT_11_1_TRACEABILITY.md).

## ADR 11.1-15 — Authorized small-model experiment without quality promotion

The user approved a smaller local setup after reporting persistent RAM pressure.
Install Qwen3 0.6B and a native `ppm-small` preset with 2,048 context/512 output defaults;
thinking off and immediate unload are launcher/API controls. Do not lower the 4B gate
or the 2 GiB headroom floor. Fresh RAM allowed the experiment alongside the full stack.
The measured 1,138 MiB server+runner peak sets the new model reservation to 1,536 MiB
after 25% margin/upward rounding. This is separate from the original 4B reservation.

Four local requests suffice for this setup: two simple controls passed, while actual
project-format initial/one-item replacement both failed unchanged hard checks. Keep
the disabled profile, exhausted root counters and candidates; native chat usability
does not qualify project classes. The preset must not be used to evade the failed
case's two-attempt cap. The sampler now uses process ancestry, and no server-only
sample is labeled model memory. Immediate-unload runs cannot be counted as warm
benchmarks. See [results/limitations](../../03-sprints/active/sprint-11.1/OLLAMA_SMALL.md).

## ADR 11.1-14 — Complete benchmark code with explicit unqualified-model disposition

The user requested completion of the documented sprint. Implement the missing T12
runner/corpus/review workflow while retaining the user's prior local-testing deferral.
The corpus has 108 draft synthetic labels, twelve/six held out per task class; labels
are excluded from requests. Independent review is an external gate, never fabricated
by a script or inferred from span/schema validity. Reviewed report/candidate hashes
bind semantic judgments to actual outputs. All real qualification thresholds remain.

The local runner accepts only the bundled synthetic set and disabled installed local
profiles. At most thirty explicitly selected measurements per invocation; a quality
fixture is one analysis/attempt and gets no automatic repair. Persistent quality
counters allow at most two attempts for a model/corpus/case/context/output condition;
unknown outcome stops future runs. Up to five explicitly requested warm repeats are
timing measurements, never extra semantic votes or recovery. Local exclusive locking
and disabled production local profiles separate this operator benchmark from SQL-
admitted tenant work. It does not claim to replace production admission. Memory is
sampled from the Windows host; model working-set peaks are sampled process sums.
Residency stays bounded at the existing 60 seconds. Cold state is observed rather than
forced by unloading models. No missing CPU/GPU/stack evidence is filled with estimates.

The optional generalized C6 cloud benchmark, native Puter free driver and embeddings
remain disabled/deferred. Do not change the three-admission Groq diagnostic allowance,
remove its history or obtain paid credit to close a quality gate. The plan expressly
permits useful deterministic/keyword operation when no profile qualifies. T12 code
completion and AT17 real-model acceptance therefore have separate statuses. Normal
rollout is outside T14's implementation authorization. See [workflow](../../03-sprints/active/sprint-11.1/BENCHMARK.md).

## ADR 11.1-13 — User-selected free-tier providers and local setup

The user selected Groq/OpenRouter/Mistral AI and confirmed free-tier accounts during remaining setup. Add native bounded JSON-schema transports through the same qualification/egress/key-binding/SQL account scopes, without changing limits or introducing an SDK. Metadata verification uses fixed authenticated GETs only; keys and hashes remain in ignored operator files. Credentials alone cannot activate a profile. Moving `latest`/automatic routing aliases are denied; Mistral uses a dated ID.

OpenRouter additionally pins one exact free model/upstream, checks a current zero-price endpoint catalog and sends zero max-price, no fallback, required-parameter and ZDR/data-denial controls. Ollama 0.40.5/Qwen3 4B are installed, local cloud is disabled and one model/generation/4096 context are configured. Fresh Windows-memory inventory replaces guessing from download size; this tool is not a production monitor. See [setup](../../03-sprints/active/sprint-11.1/PROVIDER_SETUP.md) and [receipts](../../verification/sprint11_1/IMPLEMENTATION.md).

## ADR 11.1-12 — implementation refinements under unchanged limits

Evidence: `model_contracts.py`, `agent_context.py`, `agent_runtime.py`, `0015_agent_task_runtime.py`, focused tests and [implementation receipts](../../verification/sprint11_1/IMPLEMENTATION.md).

Mode-specific JSON schemas omit unused payload definitions to fit conservative input accounting under 4096 context. Oversized whole-source/rubric contexts produce explicit unavailable scope and a narrowed-selection follow-up; automatic arbitrary source-window decomposition is deferred. Required IDs remain in the denominator. A truncated/invalid section gets at most one fresh smaller one-item replacement with unprocessed gaps, never JSON concatenation or increased output tokens.

Equal digits elsewhere in input cannot prove units, periods or numerical causality. Numerical model prose must be an exact statement inside its cited original span; free prose can refer to canonical calculated metrics in words. This conservative hard gate reduces unsupported-number risk without claiming semantic truth. Qualification must measure its effect on useful interpretations.

Optional critique is a non-required DAG node after initial sections, eligible only for material high-severity/hypothesis/conflict items and a qualified semantic-review profile. It shares the original attempt budget. Critique agreement is model review only; unsupported upstream claims and transitive synthesis are withheld while immutable sections remain. Missing evaluator eligibility leaves interpretations unreviewed.

Analysis parents must be inserted before task dependencies are checked through RLS. Canonical deterministic Decimal values cross the task checkpoint JSON boundary as exact strings, as they do in legacy publication. Unknown local attempts remain globally blocking until an operator verifies termination, including after a lease expires. Rate-limit settlement records bounded Retry-After cooldown on the shared scope. Normal 0012 and frozen 0001–0014 remain unchanged.

V2 Gemini requires the legacy provider selector disabled and a profile daily limit no higher than the existing authorized ceiling. Existing confirmation/key fields stay intact. This prevents ongoing mixed legacy dispatch from bypassing v2 account scopes without altering the legacy path when v2 is off. A future real-cloud transition must quiesce old calls and account for remaining provider quota; old usage is not automatically imported. Cloud remains disabled in this checkpoint.

## Serious alternatives

Ratings below are engineering judgments relative to this repository, not benchmark results. Good/mixed/poor expresses expected fit; every column is addressed to avoid choosing complexity by fashion.

| Criterion | A: existing one batch + patches | B: bounded native DAG + durable sections (selected) | C: LLM planner + graph framework | D: nine independent agent services |
| --- | --- | --- | --- | --- |
| Correctness | mixed: shared broad prompt | good: scoped contracts, deterministic math | mixed: planner needs validation too | mixed: many contracts/disagreements |
| Reliability | mixed: batch all-or-nothing | good: persisted sections | good if integrated, migration risk | poor initial operations burden |
| Context preservation | mixed: whole snapshot | good: manifest and evidence refs | good only with external state | mixed: repeated context distribution |
| Output recovery | poor: 512 shared | good: small sections/bounded repairs | good, requires same controls | mixed: more calls, no intrinsic recovery |
| RAM/compute | good | good: one local slot | mixed: planner overhead | poor if separately loaded |
| Quota efficiency | good calls, poor useful completion | good: zero-call domains/selection | poor: planner/judge calls | poor: minimum nine calls |
| Latency | low if valid | bounded; sequential local may be slow | added planner latency | parallel cloud faster, costly |
| Cost safety | existing guard | explicit eligibility and shared accounting | external policy still required | difficult distributed admission |
| Complexity | low | moderate within existing runtime | high integration/dependency cost | very high |
| Testability | existing fixtures | pure plan/router and crash tests | framework plus LLM planner matrix | distributed test burden |
| Observability | batch trace | task/attempt trace | useful graph trace, duplicated job truth risk | cross-service tracing needed |
| Security | prompt role separation | physically scoped requests/RLS | tool/planner attack surface | service identities/egress surface |
| Maintainability | easy but inadequate recovery | fits student-sized modular monolith | framework churn and second abstraction | excessive for one developer |
| Compatibility | highest | additive tables and facade | replacing native graph adds migration | substantial rewrite |
| Sol implementation | simple but misses requirements | ordered incremental seams | more redesign/integration | broad risky work |

A synchronous request-only orchestrator is rejected because durable jobs already exist and browser disconnects must not own execution. A new queue (Temporal/Kafka/etc.) is unnecessary. Unbounded agent debate is incompatible with four attempts and makes agreement look like correctness. One stronger LLM for all nine roles remains a benchmark comparator, not the architecture, because it retains shared context/truncation failure. A later LLM planner may only propose validated allowlisted task templates after deterministic planning proves insufficient in a measured product scenario.

## ADR 11.1-01 — Extend existing durable native execution

Requirements R01/R06/R07. Reuse `ai.Runtime`, `ai_worker`, `durable_jobs`, outbox, live authority and budgets; add bounded task checkpoints. PostgreSQL is truth, Redis/Celery delivers wakeups. No new framework. This meets restart requirements with less replacement risk. Revisit only if measured workflow needs include durable multi-day waits beyond existing job capabilities, not merely because a framework supports graphs.

## ADR 11.1-02 — Nine capabilities with shared deterministic services

R02/R11. Keep exact nine stable IDs because source requirements and frontend already use them. Financial/schedule/resource reuse metric services; sentiment retains its privacy-safe aggregate; PMO uses deterministic reconciliation; Executive retains a bounded fallback briefing. These services form a reliable baseline for the nine specialist roles. Each role may additionally use qualified model reasoning under ADR 11.1-11. Missing evidence produces explicit unavailable interpretation, not a synthetic answer. Nine roles do not require nine calls per run or nine loaded models.

## ADR 11.1-03 — Deterministic planner and policy router

R03/R04. Plan from request mode, evidence and fixed templates. No LLM has authority over money, tool names, scope, retry counts or dependencies. Capability and authorization are hard filters; preference/latency rank eligible models. Models can be reassigned without changing domain workers. Reject fixed provider per agent because outages/quota/capability vary independently of business role.

## ADR 11.1-04 — Preserve ceilings; split work rather than silently enlarge

R05/R07. Maintain 512 output tokens/attempt, four total attempts and 90 s run deadline. Select up to three initial semantic sections, reserve at most one recovery/evaluation slot when available. Large assessments report unprocessed question IDs and require explicit narrowed subsequent runs; no auto-loop that evades per-run controls. New local 22 s timeout matches the longest existing completion timeout; faster/smaller fallback is benchmarked. Increasing limits is a separate documented decision with evidence, never a recovery action.

## ADR 11.1-05 — Validation layers and epistemic labels

R08. Exact spans, deterministic arithmetic and schema acceptance are hard gates; semantic interpretation is provisional. No model self-confidence threshold or majority-vote truth. Optional critique can identify unsupported claims, never manufacture evidence. Published findings preserve disagreement and show semantic-review status. Human approval remains independent and cannot make a stale source current.

## ADR 11.1-06 — Fail-closed zero spend and provider scope

R04. Default local-only, cloud false. Existing key-bound Gemini confirmation remains non-expiring; do not introduce a daily reapproval requirement. Free-tier classification is tied to provider project/account and authorized model/operation, not arbitrary zero prices. Billing-tier change or credential/project/model change invalidates eligibility. Current account state cannot be guaranteed by client-side prices; strict zero-spend deployments keep cloud disabled if no provider-enforced no-billing boundary is established. Groq is a disabled candidate with mock contract tests until organization tier, model and data policy are authorized.

## ADR 11.1-07 — Local model is runtime, not control plane

R10. Benchmark Qwen3 4B quantized first, Qwen3 1.7B as lower-memory alternative, Gemma3 4B as comparator; do not declare a quality winner. Share one loaded chat model, 4096 configured context, concurrency one. EmbeddingGemma is an optional later local projection; keyword retrieval makes local-only useful without vector/model loading. No nine-model residency. See sources/setup for verified APIs and benchmark gates.

## ADR 11.1-08 — Immutable results and compatibility

R06/R09/R12. Add runtime-v2 task tables, preserve old runs/reviews and migration files. Version request fingerprints/output rules; do not attach old reviews to newly split/merged item identities. Legacy routes/statuses remain; new fields are additive and v2 inputs opt in through deployment flag. New run references a prior run for a user-directed narrowed retry; it does not mutate history or reset a hidden budget.

## ADR 11.1-09 — Explicit uncertainty and deferred capabilities

R08/R11. No trained sentiment, individual personnel assessment, staffing optimizer or causal predictor is introduced. Sources and later sprint requirements remain preserved. Model selection, token fitting, context quality and cold-start latency are unresolved until measured; defaults and reconsideration triggers are in risks. This is intentional qualification work, not an incomplete orchestration design.

## ADR 11.1-10 — Async v2 transport using already locked HTTPX

R03/R07. Use `httpx.AsyncClient` for v2 adapters, with one scoped client per worker event loop, bounded response reading, explicit connect/read/total timeouts, redirects disabled and environment proxy inheritance disabled for the private Ollama route. Promote the already locked httpx package to runtime dependencies when implementing T04; do not upgrade its version without a separate compatibility check. This is justified by current urllib calls surviving coroutine cancellation in executor threads. Retain legacy facade while migrating. Async disconnect improves local resource control but does not promise cancellation of upstream generation. New framework/SDK dependencies remain unnecessary.

## ADR 11.1-11 — On-demand AI interpretation across all nine roles

R02/R08/R10/R11. The user requested preserving specialist intelligence after discussing the limits of fixed rules. This decision supersedes the initial six-deterministic/three-semantic role restriction. Python remains authoritative for arithmetic, scores, scope, validation, reconciliation and execution; all nine role definitions support an optional semantic task class with explicit evidence and qualification gates. Financial and schedule workers can explain narrative causes and propose mitigations, resource can interpret authorized aggregate constraints, PMO can synthesize cross-domain implications, and Executive can produce audience-specific explanations. These are evaluated interpretations, not numerical or causal truth.

Sentiment is subject to unchanged privacy boundaries. The current blocker count alone normally does not justify a model call; optional team-support advice may use the permitted aggregate only when the request warrants it. Raw notes, individual labels and emotional diagnosis are not enabled by this revision. More capable sentiment inputs require a separately reviewed data contract.

Rejected alternatives: the initial permanent role split saves calls but limits analytical depth; nine mandatory calls waste resources on numerical or empty inputs; unconditional AI narration can merely paraphrase a count. The selected design uses per-role `interpretation_reason`, separate base/semantic coverage and goal-aware selection. The four-attempt/512-token/90-second limits stay unchanged. A request exceeding them is partial or requires a narrowed explicit run; no automatic larger budget is implied.

Acceptance: every role has a qualified interpretation path and a useful deterministic/missing-evidence fallback; metrics-only mode makes zero calls; financial/schedule/resource text fixtures and PMO/Executive synthesis fixtures show added reasoning with exact evidence and unchanged numbers. Tests must prove a selected role is not excluded by the former fixed split. Model quality must be measured by task class, including the newly available classes, before activation.
