# Known limits and future solutions

Updated 25 October 2026. This is a consolidated register of known material limits, not a
claim to have discovered every possible defect. Historical evidence and future
acceptance are linked so unresolved requirements remain visible.

| Area | Current limit and user impact | Usable approach now | Future solution and evidence needed |
| --- | --- | --- | --- |
| Broad agent reasoning | AT17 blocked; independent audit rejected a 12-output sample after 20 calibration calls/42 role outputs. No held-out provider calls were made | Canonical metrics and closed-choice guided review | Improve narrow prompts/context or assess compatible models within existing accounts; freeze a new strategy, independently review labels, measure held-out accuracy and abstention per role |
| Semantic scoring | Free models have not qualified for reliable rubric interpretation | Original deterministic assessment scores and authorized human review remain authoritative | Qualify rubric matching with missing/conflicting evidence; preserve original/suggested/approved score separation |
| Factual accuracy | Structured JSON constrains form but does not prove a claim is true | Guided API outputs contain only IDs; source wording/numbers come from the application | Independent output evaluation and numerical/source-consistency measurements before broader prose |
| Selection quality | An API can select a less useful observation or select nothing | All nine manual checklists remain accessible; no hidden certainty score | Collect explicit feedback and evaluate selection usefulness; omit model selection if it adds no measurable value |
| Nine roles / three APIs | Roles share three account quotas and each guided run assists one role | Gemini: financial/schedule/resource; Puter: risk/governance/agile; Groq: team support/PMO/executive | Larger evidence sets need user-driven pagination/cached reusable reports; any batch expansion must be measured against existing caps |
| Output/context limits | General v2: 512 output tokens, four attempts/run, two/section, 24 nodes, 90 seconds; bound context 80 KB before DB binding | Guided requests use up to eight observations, two selections, one call, 128 output tokens and no retry | Bounded sections and measured compact schemas; never concatenate truncated JSON or silently raise spend/output limits |
| Free account availability | Free allowance can exhaust or change; no app can independently guarantee account billing state | Confirmed free accounts, pinned configured models, explicit $0 policy and visible fallback | Periodic operator account review; requalify replacements explicitly. No automatic paid upgrade |
| Shared quota accounting | Retained local benchmark usage and database usage originate in different historical ledgers | Preserve all ledgers; guided ceiling 50/day/account after account-specific checks; no concurrent benchmark runs | A single authoritative quota service for every provider caller, including benchmark tools; preserve unknown outcomes and cooldowns |
| Puter monthly credit | 50/day is a request ceiling, not guaranteed sustained throughput for arbitrary token sizes; other account usage shares its monthly credit | Verified 962.41/1,000 credits remaining; small observed guided calls project to about 226 credits for 50/day over 31 days; checklist fallback on exhaustion | Add monthly credit reservation/telemetry and representative payload costing; recheck current model prices and allowance |
| Provider credentials | Only supplied Groq/Gemini/Puter accounts are part of this design; other configured candidates are not usable approvals | Reuse existing private keys, never send them to the browser | Key rotation through operator configuration; additional keys are optional and not required for this pilot |
| Ollama / local RAM | Prior local project-format tests failed and available RAM is insufficient for the intended models alongside the stack | Ollama stays stopped; no local inference dependency | Optional later evaluation on adequate hardware; measure memory, latency and quality before promotion |
| Fine-tuning | No verified free weight-training route for the configured accounts; authored examples were prompt references, not training | Narrow model responsibilities and deterministic validation | Licensed, representative data; an actually supported training host; evaluation of whether gains justify cost. Do not label prompting as fine-tuning |
| Missing/stale data | No current evidence can mean unavailable, not zero or healthy; partial measures omit inputs | Explicit labels and manual evidence-collection checklists; source changes withdraw API selections | Improve source freshness/coverage and outcome history; Sprint 12 connector/data work |
| Team privacy | Under-five groups and unauthorized raw workforce data cannot support team interpretation; blocker counts are not emotional sentiment | Existing minimum-group/Admin checks; aggregate-only support guidance | Evaluate consented team-level labels and false positives; never infer individual health or performance |
| Governance / agile | Guided mode sees only rubric presence or sprint status; it cannot read policy text or assess practice quality | Manual role-specific checklists and normal assessment workflow | Broad interpretation remains behind per-role evaluation; model-generated compliance certification is out of scope |
| PMO / executive | Guided API observations cover the selected project, not a comprehensive portfolio strategy | Manual coordination/escalation checklist and existing authorized dashboards | Qualify cross-project synthesis with complete permitted-cohort and missing-data disclosures |
| User permissions | Broad analysis still requires Admin; non-Admin guided execution requires an explicit user/project grant and current source access | Alok, Hement, Blaze and Ashu have verified guided access and demo membership under 0016; business roles unchanged | Extend only through reviewed project grants; retain revocation, source visibility and budget protections |
| Documents / retrieval | Guided mode deliberately excludes raw text; full semantic extraction/retrieval quality is not accepted | Existing scoped document/evidence browsing and keyword paths | Measure extraction/citation/retrieval for required formats, version revocation, injection, OCR and retention; keep unknowns visible |
| Historical labels / forecasts | Genuine suitable history, target definitions, leakage checks and calibrated forecasts are not yet delivered by Sprint 12/13 | Operational metrics and clearly labeled synthetic demo data | Sprint 12 legitimate datasets/temporal splits/baselines/model cards; Sprint 13 eligible serving, drift and rollback |
| Connectors | Live authority, unattended rotation/session-expiry and reviewed source conflicts need their Sprint 12 evidence | Existing authorized imports/fixtures within documented limits | Narrow service principals, versioned conflict resolution, real authorized sync, cursor/rate/recovery checks |
| Copilot and automatic changes | Complete project-aware copilot and approved action workflows are future work | Read-only checklists; ordinary project forms and human decisions | Sprints 14–15 bounded analytics tools and version-safe approved workflows |
| Transformation / simulation | Full transformation outputs, decision tracking and conserved scenario application are future work | Existing current-state planning records | Sprints 16–17 implement and validate these modules without replacing source records |
| Graph / benchmarking | No accepted full knowledge graph or comparable internal benchmark product | Existing relational data and scoped dashboards | Sprints 18–19 rebuildable access-controlled graph and privacy-safe compatible cohorts |
| Meetings / reports / alerts | Full meeting intelligence, scheduled multichannel reports and audio briefing remain future scope | Existing documents and available exports only | Sprints 20–21 consent, deduplication, transcript/source fidelity, authorized recipients and delivery evidence |
| Account / production security | Local controls/tests do not prove full all-surface security, passkey recovery or production readiness | Loopback local pilot and current tenancy/session controls | Sprints 22–23 passkeys, threat testing, secrets/TLS/deployment and incident/recovery evidence |
| Scale / latency / uptime | Small local tests do not establish enterprise scale, 99.9% uptime, RTO/RPO or latency targets | Bounded jobs, small requests and explicit local performance observations | Representative load tests, monitoring interval, restore drills and percentile reporting on named hardware |
| Operational availability | Docker services can be stopped after host restarts; the full stack still uses RAM even with Ollama off | Documented start command and actual health checks | Measured resource sizing and narrower optional-service startup; future deployment operations |
| Review independence | This engineering review and CodeRabbit's earlier reviews are AI reviews, not human acceptance | Record the reviewer type and exact test evidence | Independent human product/security review before a production release |
| Documentation drift | Older status files contain dated states and prototype scope; they cannot all be treated as current | This register and the newest handoff supersede dated entries | Keep release evidence and deployment receipts tied to source revision and environment |
